What the dead web still publishes

Before paying for discovery, check what a site already publishes. A fresh probe found a recognized sitemap or feed on 38 of 60 selected domains. The failures show why a crawler needs to distinguish absence from an unanswered request.

Nathaniel RobertsonNovember 2, 2026v1.2

A sitemap can supply a list of URLs without making a crawler discover every link itself. A feed can expose recent entries. Neither tells you where a page ranks in a search engine. That distinction decides which job the free structured web can do, and which job needs a different source.

I tested a fixed list of 60 domains across 12 categories, five per category. It is deliberately varied and hand-picked. It is not representative of the web, and the percentages below describe only this list, this method, and this execution environment.

What the probe actually did

The run started at 2026-11-02T01:50:54.055204+00:00 and finished at 2026-11-02T01:56:11.119786+00:00. Rig v1.2 used eight concurrent domain workers, with requests within a domain made sequentially and a 0.4-second pause between attempts. Each request had a six-second elapsed deadline covering worker startup, DNS, redirects, body reads, and decompression.

For each domain: fetch robots.txt; try up to five declared sitemaps and the conventional fallback until a recognized sitemap root is found; fetch the homepage; try up to ten declared RSS or Atom links, then six conventional feed paths. RSS 2.0, RSS 1.0, and Atom are recognized. Final redirect URLs are recorded, and relative feed links are resolved against the final homepage and its first HTML base URL.

Recognised means the XML root matches a supported format. It does not mean that the file is populated, complete, correctly maintained, or that its listed URLs resolve. One of the 34 recognized sitemap roots had zero entries.

The useful number, and its denominator

38 of 60 domains, 63.3 percent, supplied at least one supported format through these checks. 22 did not. The latter is a failed discovery result, not a claim that those sites publish nothing.

The request ledger contains 485 explicit attempts, including 166 deadline failures. That is a substantial access limitation. A different deadline, network, execution environment, user-agent, or discovery route could find more. No inferred bot policy is assigned to a timeout, a reset, or a bare HTTP status.

The probe can prove that it retrieved a structured file. A failed request cannot prove that the file does not exist.

Elapsed timings are published in the JSON summary, with denominators. They include client overhead and automatic redirects, and the six-second deadline censors slower observations. They are useful for explaining this run's cost, not for ranking servers or comparing directly with the earlier v1.0 run.

What this means for a research job

For a content inventory, start with a site's own declarations and test whether they are useful. That may remove an unnecessary discovery pass. For historical search results, ranking, or search-engine features, use a source that actually measures those things. A sitemap is not a substitute for a SERP API.

This experiment does not benchmark SearchApi's product, any competing vendor's product, or paid crawling. It measures the availability of selected public endpoints through one stated procedure. A fair product comparison would need a shared task, ground truth, repeated runs, and comparable access conditions.

Scope

  • No random sampling, geographic comparison, controlled time series, or estimate of the whole web.
  • Sitemap indexes are not traversed. Their entry counts refer to child sitemap elements, while URL sets count URL elements.
  • Discovery is bounded: first five declared sitemaps, first ten homepage feed links, and six fallback feed paths. Omitted candidates are counted in the JSON.
  • Publisher timestamps are declarations. This article makes no verified content-freshness claim from them.
  • HTTP timings include subprocess startup and transfer overhead. Request deadlines and network conditions materially affect the findings.

Reproduce it

From the repository root:

python3 dead-web/deadtech_bench.py dead-web/seeds.txt new-run.json --timeout 6 --workers 8 --pause 0.4
python3 dead-web/analyse.py new-run.json --json
python3 tools/verify_run.py new-run.json

Use a new output filename. The run records its seed hash, script hash, Python version, timeout, concurrency, pacing, every explicit request, final redirect URLs where available, and decoded-body hashes. The CLI also saves decoded response bodies locally so its selected parse results can be independently checked. The repository publishes extracted evidence and hashes; it does not redistribute homepage or feed contents.
